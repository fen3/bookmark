从「书签页」到「AI 导航」：一次对话式改造日志

2026-10-30 开发日志 bm.fenv.net

这个仓库原本叫 bookmark，是一个很朴素的个人书签页：一个二维数组装着几十个链接，脚本拼成绿色小方块，用 flex 排版，十多年没怎么动过。功能上它没问题，但每次想找一个新工具，都得先翻浏览器收藏夹。

于是有了这次改造：不写新项目，直接把老书签页重构成一个 AI 工具导航站，并且仍然用原来那套零构建的静态部署方式。整个过程基本是在对话里完成的——我说需求，AI 改代码，我验收效果。

起点：只提了一句话

「改一下，做成一个 AI 网站导航。」

没有 PRD，没有设计稿。这句话能落地，是因为老项目的结构足够简单：一个 index.html、一个 style.css，数据和渲染都挤在页面里的内联脚本。改造面小，反而让「重写」比「渐进式修改」更划算。

第一步：把数据从「行」改成「分类」

原来的数据结构是 sites 二维数组，每行 4 个、按位置硬性排布，语义全靠我叫得出来。改造后换成按分类组织：

  • 每个分类一个 { cat, sites } 对象，站点是 [名称, 链接, 一句话描述]；
  • 渲染不再写死 4 列，交给 CSS Grid 自适应，卡片数量和屏幕宽度都能自己适配；
  • 新增描述字段后，搜索就能同时匹配名称、描述和分类名。

分类最终定为 10 组：对话与通用、编程开发、图像生成、视频生成、音频与音乐、办公与效率、搜索与研究、模型与平台、资讯与学习，以及「本站工具」。

第二步：视觉与交互，顺手一起做

既然数据重写了，样式就不该继续沿用绿色方块。这一轮换了深色底 + 蓝紫渐变光晕，搜索框做成玻璃感圆角，卡片 hover 上浮并描边。比较实用的几个小细节：

  • 搜索：按 / 聚焦，Esc 清空，输入即筛；
  • 分类筛选：chip 与搜索可叠加，控制「同时满足」；
  • 结果计数：实时显示 显示 N / 84，无结果时给空态提示而不是留一片空白；
  • Logo：没有图标资源，就取名称首字，用名称哈希生成固定色相，保证同一个站点每次颜色一致。

移动端在 600px 以下隐藏描述文字、缩小卡片，一行两列，信息密度不至于崩掉。

第三步：先本地验收，再谈上线

改造完没有直接推送，而是起了个本地静态服务，用无头 Chrome 截图验收三个状态：初始渲染、搜索「视频」、点击「编程开发」。截图里能直接看到非匹配分组被隐藏、计数从 84 变成 10，确认逻辑对了才继续。

顺带清掉了一个历史遗留问题：sqlentity.html 末尾多了一个孤立的 </script> 标签，浏览器一直在容错，但不该留着。

第四步：上线，以及一个小插曲

这个仓库本来就挂在 GitHub Pages 上，域名 bm.fenv.net 由 CNAME 绑定。所以「部署」并不是换平台，而是把 main 推上去，等 Pages 自动构建：

  1. 把工作分支快进合并到 main；
  2. 推送 origin/main，等待 Pages 状态从 building 变成 built；
  3. 线上抓取页面，确认标题是「AI 导航」、style.css 返回 200；
  4. 再用无头浏览器截一张线上图，确认不是「构建成功但白屏」。

插曲是：本想用 Trae 内置的部署服务，但当前运行环境缺少所需的运行时上下文（TRAE_PROJECT_ID），CLI 直接拒绝了请求。既然项目本身已经有 Pages + 自定义域名这套现成链路，绕回原方案反而更快，也更符合「零构建」的初衷。

回头看，这次改造能这么快，靠的是两件事：项目足够小，以及每一步都有可验证的产物——截图、状态码、Pages 构建状态，而不是「应该没问题」。

后面的可选项有：给站点补真实 favicon（现在是首字母占位）、把 84 条数据抽成单独的 JSON 便于维护、加个「常用」置顶区。都不急，先让导航用起来。
